Express

El framework que convierte Node.js en un servidor web cómodo de usar

¿Por qué existe esto?

Node.js puede crear un servidor HTTP con unas pocas líneas, pero si quieres hacer algo real tienes que parsear la URL a mano, leer el método (GET, POST…), convertir el cuerpo de la petición de bytes a JSON, comparar rutas con cadenas… todo sin ayuda. Es tedioso y propenso a errores. Express resuelve exactamente eso: envuelve el servidor HTTP de Node y ofrece un sistema de rutas, middlewares y respuestas que hace que escribir una API sea directo al grano.

Estructura mínima

Una aplicación Express en su forma más básica:

import express from "express"

const app = express()
const PORT = 3001

app.use(express.json())   // middleware: parsea el body JSON automáticamente

app.listen(PORT, () => {
  console.log(`Servidor escuchando en http://localhost:${PORT}`)
})

express() crea la aplicación. app.listen() abre el puerto. Entre medias, todo lo que se registre con app.use() o app.get/post/…() define el comportamiento.

¿Qué es un middleware?

Un middleware es una función que Express ejecuta en orden para cada petición, antes de llegar a la ruta final. Recibe tres parámetros: req (la petición), res (la respuesta) y next (función para pasar al siguiente middleware).

app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`)  // loguear cada petición
  next()                                   // continuar
})

Si no llamas a next(), la petición queda bloqueada ahí. Si llamas a res.json() sin llamar a next(), la petición termina ahí. Así se construye la lógica en capas.

Definir rutas

Cada ruta es una combinación de método HTTP + patrón de URL + función manejadora:

// GET — obtener datos
app.get("/logros", (req, res) => {
  res.json([{ id: 1, nombre: "Primer login", puntos: 10 }])
})

// GET con parámetro dinámico — el :id captura el valor del segmento
app.get("/logros/:id", (req, res) => {
  const id = Number(req.params.id)   // params contiene los segmentos dinámicos
  res.json({ id })
})

// POST — recibir datos en el body
app.post("/logros", (req, res) => {
  const { nombre, puntos } = req.body   // funciona gracias a express.json()
  res.status(201).json({ nombre, puntos })
})

Códigos de estado HTTP

Cada respuesta lleva un número que indica si fue bien o mal. Express devuelve 200 por defecto; tú lo cambias con .status():

CódigoSignificadoCuándo usarlo
200OKRespuesta exitosa por defecto (GET, etc.)
201Creado correctamenteTras un POST que crea un recurso
400Bad RequestError en la petición (datos incorrectos o faltantes)
401No autorizadoToken ausente o inválido
404No encontradoEl recurso solicitado no existe
500Error interno del servidorError inesperado en el backend

Organizar rutas con Router

Cuando la API crece, poner todas las rutas en server.ts se vuelve inmanejable. Express ofrece Router para separar las rutas en archivos propios:

// routes/logros.ts
import express from "express"
const router = express.Router()

router.get("/", ...)       // responde a GET /logros
router.get("/:id", ...)    // responde a GET /logros/1, /logros/2, etc.
router.post("/", ...)      // responde a POST /logros

export default router

// server.ts
import logrosRouter from "./routes/logros"
app.use("/logros", logrosRouter)   // monta el router bajo /logros

Las rutas dentro del Router son relativas al prefijo que se le da en app.use(). El / dentro del router equivale a /logros en la URL real.

En webLogrosApp

El punto de entrada del backend es apps/backend/src/server.ts. Registra dos middlewares globales (CORS manual + express.json()) y monta dos routers:

app.use("/auth", authRouter)
app.use("/logros", logrosRouter)

Las rutas de logros viven en apps/backend/src/routes/logros.ts. El GET / y GET /:id son públicos; el POST / aplica el middleware authMiddleware antes del handler:

router.post("/", authMiddleware, async (req: Request, res: Response) => {
  const { nombre, puntos }: { nombre: string; puntos: number } = req.body ?? {}

  if (!nombre || !puntos) {
    res.status(400).json({ error: "Faltan campos: nombre y puntos" })
    return
  }

  const nuevoLogro = await prisma.logro.create({ data: { nombre, puntos } })
  res.status(201).json(nuevoLogro)
})

De la misma manera, apps/backend/src/routes/auth.ts expone POST /auth/register y POST /auth/login.

Async/await en las rutas

En cuanto las rutas tocan la base de datos, necesitan ser asíncronas. Express 5 (que usa este proyecto) maneja las excepciones de funciones async automáticamente — en Express 4 había que envolverlas a mano en un try/catch o usar un wrapper.

router.get("/", async (_req: Request, res: Response) => {
  const logros = await prisma.logro.findMany()
  res.json(logros)
})

Gotcha: olvidarse de return tras enviar la respuesta

En Express, enviar una respuesta (res.json(), res.status().json()…) no detiene la ejecución de la función. Si después hay más código que intenta enviar otra respuesta, obtendrás el error "Cannot set headers after they are sent". La solución es añadir return justo después de la respuesta de error:

if (!logro) {
  res.status(404).json({ error: "Logro no encontrado" })
  return   // ← sin este return, el código de abajo también se ejecuta
}
res.json(logro)
