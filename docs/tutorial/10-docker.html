Docker

Empaquetar una aplicación en un contenedor reproducible en cualquier máquina

¿Por qué existe esto?

Antes de Docker, preparar un servidor era una odisea: instalar la versión correcta de Node, la versión correcta de PostgreSQL, configurar variables de entorno, rezar para que el sistema operativo del servidor coincidiera con el de desarrollo… Un error típico era «en mi máquina funciona». Docker resuelve esto empaquetando la app junto con todo su entorno en una imagen. La imagen se ejecuta igual en tu portátil, en el servidor de producción y en el CI de GitHub.

Conceptos fundamentales

Docker distingue entre dos cosas que es fácil confundir al principio:

ConceptoAnalogíaDescripción
ImagenPlano de un apartamentoPlantilla inmutable con el sistema de archivos, dependencias y comandos de arranque. Se construye una vez con docker build.
ContenedorEl apartamento habitadoInstancia en ejecución de una imagen. Se puede parar, reiniciar o borrar sin tocar la imagen.
VolumenCajón fuera del apartamentoAlmacenamiento persistente que sobrevive cuando el contenedor se elimina. Los datos de PostgreSQL viven aquí.
RegistryTienda de planosServidor donde se guardan y distribuyen imágenes. Docker Hub es el público; GHCR (GitHub Container Registry) es el que usa este proyecto.

Comandos básicos

docker compose up -d        # levantar todos los contenedores en segundo plano
docker compose down         # parar y eliminar contenedores (los datos del volumen sobreviven)
docker ps                   # ver contenedores corriendo
docker logs weblogros_backend   # ver la salida de un contenedor
docker exec -it weblogros_db psql -U admin -d weblogros   # entrar a la BD

docker-compose.yml — orquestación local

Compose describe todos los servicios del proyecto en un solo archivo YAML. Con un único comando se levantan todos coordinados.

En webLogrosApp

El archivo docker-compose.yml define 4 servicios para desarrollo local:

services:
  db:
    image: postgres:16
    container_name: weblogros_db
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: admin123
      POSTGRES_DB: weblogros
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

  backend:
    build: ./apps/backend
    container_name: weblogros_backend
    environment:
      DATABASE_URL: postgresql://admin:admin123@db:5432/weblogros
      JWT_SECRET: clave_secreta_muy_larga_y_aleatoria_weblogros_2026
    depends_on:
      - db

  frontend:
    build: ./apps/frontend
    container_name: weblogros_frontend
    environment:
      BACKEND_URL: http://backend:3001
    depends_on:
      - backend

  nginx:
    image: nginx:alpine
    container_name: weblogros_nginx
    ports:
      - "80:80"
    volumes:
      - ./infra/nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - frontend
      - backend

volumes:
  postgres_data:

Los contenedores de producción (docker-compose.prod.yml) añaden un quinto servicio — Watchtower — que se encarga del auto-despliegue automático al detectar nuevas imágenes en GHCR.

Dockerfiles — construir la imagen

Cada aplicación tiene su propio Dockerfile. Docker lo lee línea a línea y construye una imagen por capas.

Backend — apps/backend/Dockerfile

FROM node:20-alpine

WORKDIR /app

COPY package*.json ./
COPY prisma ./prisma      # ← necesario ANTES de npm install
RUN npm install

COPY . .
RUN npm run build         # compila TypeScript → dist/

COPY entrypoint.sh ./
RUN chmod +x entrypoint.sh

EXPOSE 3001

CMD ["./entrypoint.sh"]

El apps/backend/entrypoint.sh hace dos cosas al arrancar el contenedor:

#!/bin/sh
npx prisma migrate deploy   # aplica migraciones pendientes en la BD
exec node dist/server.js    # inicia el servidor

Esto garantiza que la base de datos siempre está actualizada antes de que el servidor empiece a atender peticiones.

Frontend — apps/frontend/Dockerfile

FROM node:20-alpine

WORKDIR /app

COPY package*.json ./
RUN npm install

COPY . .
RUN npm run build         # genera build de producción Next.js

EXPOSE 3000

CMD ["npm", "run", "start"]

Capas y caché — el truco de la velocidad

Docker guarda cada paso del Dockerfile como una capa. Si una capa no cambia, la reutiliza del caché. Por eso el patrón de los Dockerfiles es siempre:

  1. Copiar solo package*.json (y prisma/ en el backend)
  2. Ejecutar npm install
  3. Luego copiar el resto del código

Así, si solo cambias código fuente (no dependencias), Docker reutiliza la capa de npm install y el build es segundos en vez de minutos.

Por qué el backend copia prisma/ antes de npm install

El package.json del backend tiene un script postinstall: "prisma generate". Este script se ejecuta automáticamente al terminar npm install y necesita leer el schema.prisma para generar el cliente TypeScript. Si prisma/ no está copiado en ese momento, el build falla con «schema not found».

.dockerignore — qué no copiar

Sin .dockerignore, el COPY . . copiaría node_modules local (miles de archivos) encima de los instalados dentro del contenedor — corrompiendo el build. El .dockerignore funciona igual que .gitignore pero para Docker:

# backend/.dockerignore y frontend/.dockerignore
node_modules
dist          # solo backend
.next         # solo frontend
.env          # las vars de entorno llegan por docker-compose, no por el .env local

Variables de entorno en Docker

El .env local está en .dockerignore y no entra al contenedor. Las variables se definen directamente en el docker-compose.yml:

backend:
  environment:
    DATABASE_URL: postgresql://admin:admin123@db:5432/weblogros
    JWT_SECRET: clave_secreta_muy_larga_y_aleatoria_weblogros_2026

frontend:
  environment:
    BACKEND_URL: http://backend:3001   # nombre de contenedor, no localhost

Gotcha: localhost no existe dentro de un contenedor

Dentro de un contenedor, localhost se refiere al propio contenedor, no al host ni a otro contenedor. Para que el backend hable con la base de datos, la URL usa @db:5432 — donde db es el nombre del servicio definido en Compose. Docker crea una red interna y resuelve automáticamente los nombres de servicio como hostnames.

Volúmenes — datos que sobreviven

Cuando un contenedor se elimina, su sistema de archivos desaparece. Los volúmenes son directorios gestionados por Docker que persisten aunque el contenedor se borre:

volumes:
  postgres_data:    # Docker gestiona dónde guarda esto en el host

Así puedes hacer docker compose down y volver a levantar los contenedores sin perder los datos de PostgreSQL. El volumen vive en el host hasta que lo borras explícitamente con docker volume rm.
