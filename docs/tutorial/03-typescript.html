TypeScript

JavaScript con tipos: detecta errores antes de ejecutar el código.

¿Por qué existe esto?

JavaScript es un lenguaje dinámico: no comprueba tipos hasta que el código está corriendo. Eso significa que un error como pasar un string donde se esperaba un number solo aparece en producción, cuando un usuario real lo descubre. A medida que los proyectos crecen (más archivos, más desarrolladores), este modelo se vuelve costoso en tiempo de depuración.

TypeScript es un superconjunto de JavaScript: todo JavaScript válido es TypeScript válido. Le añade un sistema de tipos estático que el compilador (tsc) verifica antes de ejecutar nada. Si hay un error de tipos, tsc lo señala con la línea exacta. El resultado: errores capturados al escribir el código, no al ejecutarlo.

Instalación

npm install --save-dev typescript ts-node @types/node @types/express
npx tsc --init   # genera tsconfig.json con opciones comentadas

ts-node ejecuta TypeScript directamente sin compilar a un archivo intermedio — ideal para desarrollo. @types/* son paquetes que añaden tipos a librerías escritas originalmente en JavaScript (como Express).

Tipos básicos

La anotación de tipo va después del nombre de la variable, separada por dos puntos:

const nombre: string = "Javier"
const puntos: number = 150
const activo: boolean = true
const PORT: number = 3001

Aviso

TypeScript puede inferir el tipo automáticamente en muchos casos: const nombre = "Javier" ya sabe que es string sin que lo escribas. La anotación explícita es útil cuando la inferencia no llega (parámetros de funciones, objetos complejos).

Interfaces — la forma de un objeto

Una interfaz describe la estructura que debe tener un objeto: qué propiedades existe y de qué tipo es cada una. Es como un contrato que TypeScript verifica en tiempo de compilación.

interface Logro {
  id: number
  nombre: string
  puntos: number
}

const logro: Logro = { id: 1, nombre: "Primer login", puntos: 10 }
const logros: Logro[] = [...]   // array de Logros (el [] indica "lista de")

Tipos en funciones

Se anotan los parámetros y el tipo de retorno. TypeScript verificará que la función siempre devuelva el tipo prometido:

const sumar = (a: number, b: number): number => a + b
//                    ^tipo param  ^tipo param  ^tipo retorno

Módulos en TypeScript (ES Modules)

TypeScript usa import/export en lugar de require/module.exports. El compilador los transforma al sistema que necesite el entorno de destino.

// exportar
export default router

// importar — módulo con export default
import logrosRouter from "./routes/logros"

// importar — módulo con exports nombrados
import express, { Request, Response } from "express"

Express con TypeScript

Los tipos Request y Response de Express describen qué propiedades tiene cada objeto. Así el editor autocompletará req.body, res.json(), etc., y avisará si los usas mal:

import express, { Request, Response } from "express"

const router = express.Router()

router.get("/", (req: Request, res: Response) => {
  res.json(logros)
})

router.post("/", (req: Request, res: Response) => {
  const { nombre, puntos }: { nombre: string; puntos: number } = req.body
  // TypeScript sabe que nombre es string y puntos es number
})

tsconfig.json — la configuración del compilador

tsconfig.json le dice a tsc cómo compilar el proyecto: qué versión de JavaScript generar, dónde está el código fuente, dónde dejar el resultado…

En webLogrosApp

La configuración real del backend está en apps/backend/tsconfig.json:

{
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "rootDir": "./src",
    "outDir": "./dist",
    "types": ["node"],
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "sourceMap": true
  },
  "exclude": ["prisma.config.ts", "node_modules", "dist"]
}
OpciónQué hace
target: "ES2020"Genera JavaScript compatible con Node 14+ (soporta async/await nativo)
module: "commonjs"Usa require() en el JS generado (el sistema de módulos de Node.js clásico)
rootDir: "./src"Todo el código fuente TypeScript está en src/
outDir: "./dist"El JavaScript compilado va a dist/ (se ejecuta en producción)
strict: trueActiva todas las comprobaciones de tipo estrictas (recomendado)
esModuleInterop: truePermite usar import x from "x" con librerías CommonJS
sourceMap: trueGenera mapas para que los errores de dist/ apunten a líneas de src/
excludeExcluye prisma.config.ts para que tsc no intente compilarlo (está fuera de rootDir)

Gotcha: prisma.config.ts fuera de rootDir

Si añades un archivo TypeScript en la raíz del backend (como prisma.config.ts) y rootDir apunta a ./src, tsc lanzará el error TS6059: File is not under rootDir. La solución es añadirlo al array exclude del tsconfig.json, como ya está hecho en este proyecto.

El flujo de compilación

En desarrollo y en producción el código sigue caminos distintos:

EntornoHerramientaCómo
Desarrollots-nodeTranspila en memoria al vuelo; no genera archivos .js
Produccióntsc + nodeCompila a dist/ y luego Node ejecuta el JS generado
 
# Desarrollo (ts-node via nodemon — script "dev")
nodemon --exec ts-node src/server.ts

# Producción (compilar primero, ejecutar después — script "build" + CMD en Docker)
tsc
node dist/server.js

En webLogrosApp — server.ts en acción

apps/backend/src/server.ts muestra TypeScript real en uso: imports de ES Modules, tipo explícito en PORT, y el middleware CORS escrito como arrow function tipada con los tipos de Express:

import "dotenv/config"
import express from "express"
import logrosRouter from "./routes/logros"
import authRouter from "./routes/auth"

const app = express()
const PORT: number = 3001

app.use((req, res, next) => {
  res.header("Access-Control-Allow-Origin", "http://localhost:3000")
  res.header("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS")
  res.header("Access-Control-Allow-Headers", "Content-Type, Authorization")
  if (req.method === "OPTIONS") {
    res.sendStatus(200)
    return
  }
  next()
})
app.use(express.json())

app.use("/auth", authRouter)
app.use("/logros", logrosRouter)

app.listen(PORT, () => {
  console.log(`Servidor escuchando en http://localhost:${PORT}`)
})

Fíjate en el import "dotenv/config" al principio: carga las variables de entorno del archivo apps/backend/.env antes de que cualquier otro módulo las necesite.
