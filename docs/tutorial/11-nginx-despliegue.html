Nginx y despliegue

Un único punto de entrada y un pipeline de despliegue automático de extremo a extremo

¿Por qué existe esto?

Sin un reverse proxy, el usuario tendría que acceder a :3000 para el frontend y a :3001 para la API — exponer múltiples puertos al exterior es inseguro, incómodo y hace imposible servir ambas cosas bajo el mismo dominio. Nginx resuelve esto: escucha en el puerto 80 (el estándar HTTP) y enruta cada petición al servicio correcto según la URL. Además, el ciclo de despliegue manual (modificar código → conectarse al servidor → ejecutar comandos) es lento y propenso a errores. GitHub Actions automatiza todo: un push a main dispara la construcción de imágenes, su publicación en GHCR, y Watchtower las despliega automáticamente en el servidor.

Nginx como reverse proxy

Un reverse proxy es un intermediario que recibe peticiones del exterior y las reenvía al servicio interno adecuado. El cliente no sabe que hay dos aplicaciones distintas detrás — todo parece venir del mismo servidor.

Sin Nginx:
  Navegador → tudominio.com:3000  (Next.js — frontend)
  Navegador → tudominio.com:3001  (Express — API)
  ↑ Dos puertos expuestos, CORS entre ellos, sin TLS centralizado

Con Nginx:
  Navegador → tudominio.com:80
                    │
                 [Nginx]
                /        \
           /api/*          /*
             │               │
          Express         Next.js
         (puerto 3001)   (puerto 3000)
         ← red interna →

En webLogrosApp

El archivo infra/nginx/nginx.conf es el corazón del enrutamiento:

events {}

http {
  server {
    listen 80;

    location /api/ {
      proxy_pass http://backend:3001/;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
    }

    location / {
      proxy_pass http://frontend:3000;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
    }
  }
}

Este archivo se monta como volumen de solo lectura en el contenedor de Nginx desde docker-compose.yml:

nginx:
  image: nginx:alpine
  volumes:
    - ./infra/nginx/nginx.conf:/etc/nginx/nginx.conf:ro

Anatomía del nginx.conf

DirectivaQué hace
events {}Bloque obligatorio. Vacío = usar valores por defecto (conexiones simultáneas, etc.)
listen 80Escucha peticiones HTTP en el puerto estándar
location /api/ { … }Las rutas más específicas se declaran primero. Todo lo que empiece por /api/ va al backend
location / { … }El resto (cualquier otra URL) va al frontend Next.js
proxy_pass http://backend:3001/Reenvía al backend. backend es el nombre del servicio Docker (no localhost)
proxy_set_header X-Real-IPPasa la IP original del visitante al servicio destino

Gotcha: la barra final en proxy_pass importa mucho

proxy_pass http://backend:3001/; — la barra al final hace que Nginx quite el prefijo /api antes de reenviar. Si un navegador pide /api/logros, el backend recibe /logros (no /api/logros). Sin esa barra, el backend recibiría /api/logros y tendría que definir rutas bajo /api/, lo cual es redundante.

Gotcha: http://backend:3001 — nombre de contenedor, no localhost

El contenedor de Nginx no puede usar localhost para referirse al backend — localhost dentro de Nginx es el propio Nginx. Docker Compose crea una red interna donde cada contenedor es accesible por su nombre de servicio: backend, frontend, db.

Flujo de despliegue completo

El pipeline de despliegue tiene cuatro eslabones:

1. git push → main
       ↓
2. GitHub Actions construye las imágenes Docker y las publica en GHCR
       ↓
3. Watchtower (corriendo en el servidor) detecta nuevas imágenes cada 30 s
       ↓
4. Watchtower descarga y redespliega los contenedores marcados automáticamente

Eslabón 1 y 2 — GitHub Actions

En webLogrosApp

El workflow .github/workflows/deploy.yml se activa en cada push a main:

name: Build and Push

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - uses: actions/checkout@v4

      - name: Set lowercase owner
        run: echo "OWNER=$(echo '${{ github.repository_owner }}' | tr '[:upper:]' '[:lower:]')" >> $GITHUB_ENV

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push backend
        uses: docker/build-push-action@v5
        with:
          context: ./apps/backend
          push: true
          tags: ghcr.io/${{ env.OWNER }}/weblogros-backend:latest

      - name: Build and push frontend
        uses: docker/build-push-action@v5
        with:
          context: ./apps/frontend
          push: true
          tags: ghcr.io/${{ env.OWNER }}/weblogros-frontend:latest

El resultado son dos imágenes publicadas en GHCR: ghcr.io/javierloro/weblogros-backend:latest y ghcr.io/javierloro/weblogros-frontend:latest.

Eslabón 3 y 4 — Watchtower (auto-despliegue)

Watchtower es un contenedor que vigila otros contenedores. Cada 30 segundos comprueba si hay una imagen más nueva en el registry para los contenedores que tienen la etiqueta com.centurylinklabs.watchtower.enable=true. Si la hay, descarga la nueva imagen y reinicia el contenedor.

En webLogrosApp

En docker-compose.prod.yml, backend y frontend llevan la etiqueta de Watchtower:

backend:
  image: ghcr.io/javierloro/weblogros-backend:latest
  labels:
    - "com.centurylinklabs.watchtower.enable=true"
  restart: unless-stopped

frontend:
  image: ghcr.io/javierloro/weblogros-frontend:latest
  labels:
    - "com.centurylinklabs.watchtower.enable=true"
  restart: unless-stopped

watchtower:
  image: containrrr/watchtower
  volumes:
    - /var/run/docker.sock:/var/run/docker.sock
    - /root/.docker/config.json:/config.json:ro
  environment:
    WATCHTOWER_POLL_INTERVAL: 30     # comprobar cada 30 segundos
    DOCKER_API_VERSION: "1.41"
  command: --label-enable            # solo los contenedores etiquetados
  restart: unless-stopped

Watchtower necesita acceso al socket de Docker (/var/run/docker.sock) para poder reiniciar contenedores, y a las credenciales de Docker (config.json) para poder descargar imágenes privadas de GHCR.

Servidor — Proxmox

El servidor donde corre todo es una máquina virtual gestionada con Proxmox. Proxmox es un hipervisor de código abierto que permite crear y gestionar máquinas virtuales desde una interfaz web. El proyecto aprende aquí qué significa «tener un servidor propio» frente a contratar un VPS.

Red pública — Cloudflare Tunnel + Nginx Proxy Manager

El servidor en Proxmox no tiene IP pública accesible directamente desde internet. La arquitectura de red tiene dos capas:

CapaHerramientaFunción
Túnel seguroCloudflare TunnelConecta el servidor con Cloudflare sin abrir puertos en el router. El tráfico entra por Cloudflare (que provee TLS/HTTPS en el borde) y sale por el túnel encriptado hacia el servidor
Proxy localNginx Proxy ManagerReverse proxy con interfaz web que distribuye el tráfico entre los distintos servicios de la VM. Recibe del Cloudflare Tunnel y reenvía a weblogros_nginx:8080
AppNginx (contenedor)El Nginx de la aplicación (ya visto) que enruta entre backend y frontend

¿Por qué Cloudflare Tunnel y no Let's Encrypt directo?

Cloudflare Tunnel es más sencillo en un entorno doméstico o de aprendizaje: no requiere IP pública fija, no hay que abrir puertos en el router, y Cloudflare termina el TLS en su borde (el navegador habla HTTPS con Cloudflare; Cloudflare habla por el túnel con el servidor). Let's Encrypt requeriría que el servidor sea accesible públicamente en el puerto 80/443 para el challenge de DNS o HTTP.

Bug latente: URLs hardcodeadas en el frontend

Phase 5.5 — Bug prioritario a corregir

Actualmente el frontend tiene llamadas a http://localhost:3001 hardcodeadas en varios Client Components (login, register, NuevoLogro…). Esto funciona en desarrollo porque el navegador del desarrollador tiene el backend en su localhost:3001. En producción, el navegador del visitante intenta conectarse a su propio localhost:3001, que no existe, y la petición falla silenciosamente. La solución es usar rutas relativas (/api/logros) para que Nginx actúe de intermediario, o una variable de entorno NEXT_PUBLIC_API_URL. Es el primer punto de la Phase 5.5 — Hardening.
