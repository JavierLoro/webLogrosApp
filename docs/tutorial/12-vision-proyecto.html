Visión y roadmap

Vista de pájaro: qué construimos, por qué lo construimos así y hacia dónde va

¿Por qué existe este proyecto?

webLogrosApp es un proyecto de aprendizaje progresivo: el vehículo para aprender a construir una aplicación web completa desde cero — JS → TS → Express → PostgreSQL → Docker → Prisma → Next.js → JWT → Nginx → CI/CD → Proxmox — llegando hasta los conceptos avanzados de multi-tenancy, roles, WebSockets y componentes de UI. Cada fase introduce una tecnología nueva sobre las anteriores, siempre con un producto funcional detrás para que el aprendizaje tenga contexto real. Esta página es el mapa del tesoro: si en algún momento te pierdes, vuelve aquí.

Qué es la aplicación

Plataforma multi-tenant de logros. El dueño de la plataforma (SUPER_ADMIN) la ofrece a equipos. Cada equipo aceptado recibe su espacio propio bajo la ruta /equipos/[slug], con su catálogo de logros, sus jugadores, su ranking y sus estadísticas. Un visitante sin sesión solo ve la landing publicitaria y puede solicitar acceso para su equipo.

«Multi-tenant» significa que múltiples clientes (tenants = equipos) comparten la misma instalación de la aplicación y la misma base de datos, pero cada uno ve únicamente sus propios datos. Es el modelo de SaaS como Notion, Slack o GitHub: una sola plataforma, muchos espacios separados.

Los tres roles

RolQuién esQué puede hacer
SUPER_ADMIN Dueño de la plataforma Crear equipos, aprobar solicitudes de acceso de nuevos equipos, ver todo (/admin)
TEAM_ADMIN Capitán/admin de un equipo concreto Gestionar logros y jugadores de su equipo, aprobar solicitudes de logro de sus jugadores, aprobar propuestas de la comunidad (/equipos/[slug]/admin)
PLAYER Jugador de un equipo Ver su espacio, solicitar logros («yo hice esto»), proponer publicar o implementar logros de la comunidad (/equipos/[slug]/solicitudes)

El rol de TEAM_ADMIN es contextual: alguien puede ser TEAM_ADMIN del equipo «Los Tigres» y PLAYER en «Los Leones». El rol se almacena en la relación entre usuario y equipo, no como campo global del usuario.

Cómo se gana un logro

Hay dos flujos complementarios:

  1. Asignación directa: el TEAM_ADMIN asigna directamente un logro a un jugador (por ejemplo, para reconocimientos planificados).
  2. Solicitud + aprobación: el PLAYER reclama un logro («yo completé el reto de la semana»). El TEAM_ADMIN lo aprueba o rechaza. Este flujo es una máquina de estados simple: PENDIENTE → APROBADA / RECHAZADA.

En webLogrosApp — Decisiones clave (de docs/Decisions)

Slug en la URL en vez de subdominio (/equipos/los-tigres en lugar de los-tigres.logros.jlc-dev.me): el Universal SSL gratuito de Cloudflare solo cubre un nivel de subdominio (*.jlc-dev.me). Un sub-subdominio requeriría Advanced Certificate Manager (~10$/mes) más configuración de wildcard en el Cloudflare Tunnel y middleware de Host. El slug bajo /equipos/ es gratis, simple, y migrable a subdominios en el futuro sin cambiar el modelo de datos.

/equipos/[slug] en vez de /[slug] en la raíz: un segmento dinámico en la raíz (/[slug]) colisiona con cada ruta de primer nivel. Aunque Next.js da preferencia a rutas estáticas sobre dinámicas, cada nueva página top-level se convierte en una palabra reservada que ningún equipo puede usar como slug — habría que mantener una blacklist para siempre. El namespace explícito /equipos/ hace las colisiones imposibles, la URL es autoexplicativa, y el patrón es migrable después (igual que GitHub reserva /settings pero sirve perfiles de usuario en /torvalds).

Comunidad de logros — copia independiente con atribución: cuando un equipo «implementa» un logro de la comunidad, se crea una copia totalmente independiente en su catálogo, con atribución al equipo autor («idea de Los Tigres»). La copia es editable localmente y no cambia si el original cambia. Esto preserva el aislamiento entre tenants: un equipo no puede depender del catálogo de otro ni verse afectado por sus cambios.

Lo que está activo en este momento (Phase 5.5)

El hardening es la fase donde la app pasa de «funciona en mi máquina» a «funciona de forma robusta en producción». El problema más urgente — y el primer punto — es el de las URLs hardcodeadas:

// Esto está en varios Client Components del frontend:
const res = await fetch("http://localhost:3001/auth/login", { … })
//                       ↑ En producción, el navegador del visitante
//                         intenta conectar a SU propio localhost:3001
//                         que no existe → error silencioso

// La corrección es usar rutas relativas (Nginx se encarga del resto):
const res = await fetch("/api/auth/login", { … })

La ruta de aprendizaje completa

JS → TS → Express → PostgreSQL → Docker → Prisma → Next.js → JWT
→ Nginx → CI/CD → Proxmox → Hardening → Multi-tenancy → Roles
→ Auth Hardening → Solicitudes/Admin → Aggregaciones SQL
→ Comunidad → shadcn/ui → File uploads → Testing → WebSockets

Cada tecnología de la lista es una herramienta real usada en producción. Al final de la ruta, habrás construido una aplicación SaaS completa con autenticación, autorización contextual, base de datos relacional, despliegue automatizado y tiempo real.
