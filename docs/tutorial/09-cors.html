CORS

Por qué el navegador bloquea peticiones entre orígenes distintos y cómo el servidor da permiso explícito.

¿Por qué existe esto?

Imagina que estás logueado en tu banco en banco.com. Una página maliciosa en evil.com podría ejecutar JavaScript que hace peticiones a banco.com/transferir usando tus cookies de sesión. Para impedirlo, los navegadores implementan la Same-Origin Policy: por defecto, el JavaScript de una página solo puede hacer peticiones al mismo origen (mismo protocolo, dominio y puerto).

CORS (Cross-Origin Resource Sharing) es el mecanismo que permite que un servidor rompa esa restricción de forma controlada, diciendo explícitamente: "Sí, acepto peticiones desde http://localhost:3000".

¿Qué es un "origen"?

Un origen es la combinación de protocolo + dominio + puerto. Para que dos URLs tengan el mismo origen, los tres deben coincidir exactamente:

URL Mismo origen que http://localhost:3000 Razón
http://localhost:3000/login ✓ Sí Solo cambia la ruta, no el origen
http://localhost:3001 ✗ No Puerto diferente (3001 ≠ 3000)
https://localhost:3000 ✗ No Protocolo diferente (https ≠ http)
http://midominio.com:3000 ✗ No Dominio diferente

En webLogrosApp

El frontend corre en http://localhost:3000 (Next.js) y el backend en http://localhost:3001 (Express). Aunque ambos están en localhost, los puertos son distintos: son orígenes diferentes. Sin CORS configurado, cualquier petición del frontend al backend sería bloqueada por el navegador.

El error que ves en el navegador

Cuando CORS no está configurado, el navegador bloquea la respuesta y muestra en la consola algo como:

Access to fetch at 'http://localhost:3001/logros' from origin
'http://localhost:3000' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the
requested resource.

Gotcha: Thunder Client y curl no tienen CORS

CORS es una restricción del navegador, no del servidor. Thunder Client, Postman, curl y los Server Components de Next.js no son navegadores, así que pueden hacer peticiones entre orígenes sin problema. Un endpoint puede funcionar perfectamente en Thunder Client y fallar en el navegador por CORS. Si tu API responde bien en las herramientas de prueba pero falla desde el frontend, lo primero que hay que revisar es CORS.

Cómo funciona CORS

CORS no es que el servidor "bloquee" la petición. El servidor la recibe y responde normalmente. Es el navegador quien, al recibir la respuesta, comprueba si incluye el header Access-Control-Allow-Origin. Si el header no está o no incluye el origen del frontend, el navegador descarta la respuesta y muestra el error.

Sin CORS:
  Frontend (localhost:3000)  →  petición  →  Backend (localhost:3001)
  Frontend (localhost:3000)  ←  respuesta (sin headers CORS)
  Navegador: "Este origen no está permitido" → descarta la respuesta ✗

Con CORS configurado:
  Frontend (localhost:3000)  →  petición  →  Backend (localhost:3001)
  Frontend (localhost:3000)  ←  respuesta + Access-Control-Allow-Origin: http://localhost:3000
  Navegador: "Origen permitido" → entrega la respuesta al JavaScript ✓

Preflight request — la petición de permiso

Antes de hacer peticiones "no simples" (POST con JSON, cualquier petición con headers personalizados como Authorization), el navegador envía automáticamente una petición OPTIONS previa al mismo endpoint. Es una "preflight request": pregunta al servidor si la petición real está permitida antes de enviarla.

1. Navegador  →  OPTIONS /logros
               Origin: http://localhost:3000
               Access-Control-Request-Method: POST
               Access-Control-Request-Headers: Content-Type, Authorization

2. Servidor   →  200 OK
               Access-Control-Allow-Origin: http://localhost:3000
               Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
               Access-Control-Allow-Headers: Content-Type, Authorization

3. Navegador: "OK, el servidor lo permite"
   Navegador  →  POST /logros (la petición real)
               Authorization: Bearer eyJ...

Si el servidor no responde correctamente al OPTIONS, el navegador no envía la petición real y muestra el error CORS.

Solución — middleware manual en Express

El middleware CORS se añade antes de express.json() y de cualquier ruta, para que todas las peticiones pasen por él:

En webLogrosApp — el middleware CORS real

apps/backend/src/server.ts — configuración completa. Las tres cabeceras son necesarias; falta cualquiera y el navegador bloqueará ciertas peticiones:

import "dotenv/config"
import express from "express"
import logrosRouter from "./routes/logros"
import authRouter from "./routes/auth"

const app = express()
const PORT: number = 3001

// CORS — debe ir antes de express.json() y de las rutas
app.use((req, res, next) => {
  res.header("Access-Control-Allow-Origin", "http://localhost:3000")
  res.header("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS")
  res.header("Access-Control-Allow-Headers", "Content-Type, Authorization")
  if (req.method === "OPTIONS") {
    res.sendStatus(200)
    return
  }
  next()
})

app.use(express.json())

app.use("/auth", authRouter)
app.use("/logros", logrosRouter)

app.listen(PORT, () => {
  console.log(`Servidor escuchando en http://localhost:${PORT}`)
})

Los tres headers explicados

Header Qué permite Si falta
Access-Control-Allow-Origin Qué orígenes pueden hacer peticiones Todas las peticiones bloqueadas
Access-Control-Allow-Methods Qué métodos HTTP están permitidos Solo GET está implícitamente permitido
Access-Control-Allow-Headers Qué cabeceras puede enviar el cliente Sin Authorization: el token JWT no llegaría al servidor

¿Por qué no usar Access-Control-Allow-Origin: *?

El wildcard * permite peticiones desde cualquier origen. Es conveniente para APIs públicas, pero tiene una restricción importante: no funciona con credenciales (cookies o el header Authorization). Si tu API requiere autenticación mediante token, tienes que especificar el origen exacto. En producción conviene configurar el origen desde una variable de entorno en lugar de hardcodearlo.

Alternativa — la librería cors

En lugar de escribir el middleware a mano, existe la librería oficial cors para Express:

npm install cors
npm install --save-dev @types/cors
import cors from "cors"

app.use(cors({
  origin: "http://localhost:3000",
  methods: ["GET", "POST", "PUT", "DELETE", "OPTIONS"],
  allowedHeaders: ["Content-Type", "Authorization"],
}))

El resultado es el mismo que el middleware manual. La versión manual es útil para entender exactamente qué headers se envían; la librería es más conveniente en producción y maneja algunos casos edge automáticamente (como la preflight).

CORS en producción con Nginx

Cuando el frontend y el backend están detrás de Nginx en el mismo dominio y puerto, CORS desaparece como problema. Nginx recibe todas las peticiones en https://tudominio.com y las redirige internamente: /api/* al backend, /* al frontend. Para el navegador, todas las peticiones van al mismo origen.

Sin Nginx (desarrollo):
  Frontend: http://localhost:3000  →  Backend: http://localhost:3001
  Orígenes diferentes → CORS necesario

Con Nginx (producción):
  Frontend: https://tudominio.com  →  Nginx → Backend (interno)
  Mismo origen → CORS no aplica
