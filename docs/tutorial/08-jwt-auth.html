JWT y Autenticación

Cómo un servidor sin memoria puede saber quién eres en cada petición.

¿Por qué existe esto?

HTTP es un protocolo sin estado (stateless): cada petición es completamente independiente de la anterior. El servidor no recuerda que hace un momento hiciste login. Entonces, ¿cómo demuestra el cliente quién es en cada petición?

La solución clásica eran las sesiones: el servidor guarda en memoria que el usuario X está logueado y le entrega un ID. Pero esto obliga al servidor a mantener estado y no escala bien en múltiples servidores.

JWT (JSON Web Token) invierte el problema: el servidor genera un token firmado criptográficamente y se lo entrega al cliente. En cada petición, el cliente adjunta ese token. El servidor solo necesita su clave secreta para verificar la firma — no consulta ninguna base de datos ni guarda nada en memoria. Cualquier servidor que conozca la clave puede verificar el token.

¿Qué es un token JWT?

Un token JWT es una cadena de texto con tres partes separadas por puntos. Cada parte está codificada en Base64:

eyJhbGciOiJIUzI1NiJ9 . eyJ1c2VySWQiOjF9 . abc123xyz
      CABECERA               DATOS (payload)      FIRMA
  • Cabecera: el algoritmo de firma usado (ej: HS256)
  • Payload: los datos que el servidor guarda en el token (ej: { userId: 1 }). Son legibles por cualquiera — no guardes contraseñas aquí.
  • Firma: el servidor la calcula con su clave secreta. Si alguien modifica el payload, la firma ya no coincide y el token queda inválido.

JWT es legible pero no falsificable

Cualquiera puede decodificar el payload de un JWT (no está cifrado, solo codificado en Base64). Pero nadie puede falsificar la firma sin conocer la clave secreta del servidor. Por eso, nunca guardes información sensible en el payload; guarda solo identificadores (userId, roles).

bcrypt — hashear contraseñas

Un hash es una transformación de una sola vía: dado un password puedes calcular su hash, pero dado el hash no puedes recuperar el password original. bcrypt añade además un factor de trabajo (rounds) que hace el cálculo lento a propósito, dificultando los ataques de fuerza bruta.

import bcrypt from "bcryptjs"

// Al registrar — hashear antes de guardar en la BD
const hash = await bcrypt.hash(password, 10)   // 10 = rounds (coste computacional)
await prisma.user.create({ data: { email, password: hash } })

// Al hacer login — comparar el password con el hash guardado
const esValido = await bcrypt.compare(passwordRecibido, hashGuardado)
// bcrypt.compare devuelve true o false

¿Por qué no basta con cifrar el password?

El cifrado es reversible (con la clave correcta recuperas el original). El hasheo no lo es. Si un atacante roba tu base de datos y consigue la clave de cifrado, obtiene todos los passwords. Con hashing solo obtiene hashes que son computacionalmente muy difíciles de revertir. Por eso los passwords se hashean, no se cifran.

jwt.sign y jwt.verify

import jwt from "jsonwebtoken"

const SECRET = process.env["JWT_SECRET"]!   // clave secreta del servidor

// Generar token — incluye userId en el payload, expira en 7 días
const token = jwt.sign({ userId: user.id }, SECRET, { expiresIn: "7d" })

// Verificar token — lanza excepción si es inválido o ha expirado
const payload = jwt.verify(token, SECRET) as { userId: number }
console.log(payload.userId)   // el userId que guardamos al firmar

Flujo completo: register → login → petición protegida

1. Cliente  →  POST /auth/register  { email, password }
   Servidor:   hashea password, crea usuario en BD
   Respuesta:  { id, email }   (sin token — el usuario aún no está "dentro")

2. Cliente  →  POST /auth/login  { email, password }
   Servidor:   busca usuario, compara password con hash, genera token
   Respuesta:  { token: "eyJ..." }
   Cliente:    guarda el token en localStorage

3. Cliente  →  POST /logros   Authorization: Bearer eyJ...
   Servidor:   middleware verifica token, extrae userId, permite continuar
   Respuesta:  { id, nombre, puntos }   (logro creado)

En webLogrosApp — rutas de auth

apps/backend/src/routes/auth.ts — implementación real de register y login:

// POST /auth/register
router.post("/register", async (req, res) => {
  const { email, password } = req.body ?? {}

  if (!email || !password) {
    res.status(400).json({ error: "Faltan campos: email y password" })
    return
  }

  const existe = await prisma.user.findUnique({ where: { email } })
  if (existe) {
    res.status(400).json({ error: "El email ya está registrado" })
    return
  }

  const hash = await bcrypt.hash(password, 10)
  const user = await prisma.user.create({ data: { email, password: hash } })
  res.status(201).json({ id: user.id, email: user.email })
})

// POST /auth/login
router.post("/login", async (req, res) => {
  const { email, password } = req.body ?? {}

  const user = await prisma.user.findUnique({ where: { email } })
  if (!user) {
    res.status(401).json({ error: "Credenciales incorrectas" })
    return
  }

  const esValido = await bcrypt.compare(password, user.password)
  if (!esValido) {
    res.status(401).json({ error: "Credenciales incorrectas" })
    return
  }

  const token = jwt.sign({ userId: user.id }, SECRET, { expiresIn: "7d" })
  res.json({ token })
})

Nota: tanto si el email no existe como si la contraseña es incorrecta, el servidor responde con el mismo mensaje genérico "Credenciales incorrectas". Esto es deliberado — no queremos revelar si el email está registrado o no.

Middleware de autenticación

Un middleware de Express es una función que se ejecuta antes de la ruta. El middleware de auth extrae el token del header Authorization, lo verifica y, si es válido, deja pasar la petición a la ruta. Si no, responde con 401 directamente.

En webLogrosApp — el middleware real

apps/backend/src/middleware/auth.ts — código completo del middleware:

import { Request, Response, NextFunction } from "express"
import jwt from "jsonwebtoken"

const SECRET = process.env["JWT_SECRET"]!

export function authMiddleware(req: Request, res: Response, next: NextFunction) {
  const header = req.headers["authorization"]  // "Bearer <token>"
  const token = header?.split(" ")[1]          // extrae la parte después de "Bearer "

  if (!token) {
    res.status(401).json({ error: "Token requerido" })
    return
  }

  try {
    const payload = jwt.verify(token, SECRET) as { userId: number }
    ;(req as any).userId = payload.userId   // inyecta userId en la petición
    next()                                  // continuar a la ruta
  } catch {
    res.status(401).json({ error: "Token inválido" })
  }
}

El header?.split(" ")[1] usa optional chaining (?.): si header es undefined, no lanza error, simplemente devuelve undefined.

Proteger una ruta con el middleware

El middleware se pasa como segundo argumento al método de ruta. Express lo ejecuta antes de llegar al handler:

import { authMiddleware } from "../middleware/auth"

// GET / — público (sin middleware)
router.get("/", async (req, res) => { ... })

// POST / — protegido (requiere token válido)
router.post("/", authMiddleware, async (req, res) => {
  // Solo llega aquí si el token es válido
  // req.userId tiene el id del usuario autenticado
  const { nombre, puntos } = req.body
  const logro = await prisma.logro.create({ data: { nombre, puntos } })
  res.status(201).json(logro)
})

El token en el frontend — localStorage

El frontend guarda el token en localStorage (almacenamiento del navegador persistente entre sesiones) y lo adjunta en cada petición al backend:

// Guardar al hacer login (login/page.tsx)
const data = await res.json()
localStorage.setItem("token", data.token)

// Leer y usar al crear un logro (NuevoLogro.tsx)
const token = localStorage.getItem("token")

const res = await fetch("http://localhost:3001/logros", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${token}`,   // el servidor espera este formato exacto
  },
  body: JSON.stringify({ nombre, puntos }),
})

// Borrar al hacer logout (Header.tsx)
localStorage.removeItem("token")

Variable de entorno — JWT_SECRET

La clave secreta del servidor nunca debe estar hardcodeada en el código. Se lee de una variable de entorno:

# apps/backend/.env
JWT_SECRET="una_clave_secreta_larga_y_aleatoria_minimo_32_caracteres"

¿Qué pasa si alguien descubre el JWT_SECRET?

Puede generar tokens válidos para cualquier userId. En ese momento, todos los usuarios están comprometidos y hay que rotar el secreto (cambiar el valor de JWT_SECRET), lo que invalida todos los tokens existentes y obliga a los usuarios a hacer login de nuevo. Por eso el .env nunca se sube a git.
