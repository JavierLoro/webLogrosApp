No existe propuesta. TeamMembership sí tiene role/joinedAt; UserLogro tiene fecha y unicidad userId/logroId; TeamInvitation ya guarda hash, copia cifrada, fechas y cupos.
- Se inspeccionaron las migraciones desde init hasta `20260903111951_add_solicitud_logro`: corresponden al modelo descrito. No reescribir migraciones históricas. Las nuevas columnas deberán admitir/backfillear registros existentes, sin reset obligatorio de una base con datos.
- `routes/equipos.ts`: catálogo y detalle scoped; creación directa solo acepta nombre/puntos; solicitudes propias con logro; cola admin solo PENDING; aceptar otorga mediante transacción/upsert; rechazar no recibe motivo; miembros admin devuelve id/email/role; asignación directa existe. No hay ranking, jugadores para PLAYER, actividad, dashboard, detalle admin de solicitud o propuestas.
- `routes/teams.ts`: lectura/creación de invitaciones en `/equipos/:slug/invitaciones`, lectura de membresías propias y operaciones globales. No hay revocar invitación, editar rol o retirar miembro. `routes/invitations.ts` implementa preview/join; no hay registro de quién consumió cada invitación.
- `resolveTeam`, `auth`, `teamAccess` y `types/express.d.ts` ya componen tenant, userId y membresía contextual. SUPER_ADMIN no elude el requisito de membresía/TEAM_ADMIN en estos endpoints; preservar el comportamiento real, sin ampliar permisos en esta tarea.
- Frontend: `types/api.ts` solo define Logro, AchievementRequest y TeamMember básicos; `lib/api.ts` usa `/api` y Bearer almacenado localmente. Dashboard consulta catálogo; ranking/jugadores son placeholders; el panel admin único consulta invitaciones, pendientes, miembros y catálogo. Login devuelve token, teams e isSuperAdmin, pero no identidad visible. El layout deduce el nombre del slug. No modificar autenticación para resolver identidad.

`displayName` puede ser nullable para registros previos; usar una política explícita de fallback de identidad, sin almacenar correos partidos como nombre permanente. Para el fixture todos los nombres se rellenan. El contexto evita migrar login/cookie para pintar el shell.

Puntos = suma de `Logro.puntos` de UserLogro **cuyo logro pertenece al equipo actual**. La población del ranking son las membresías actuales, incluidos TEAM_ADMIN; no filtrar todos los usuarios globales ni sumar logros de Lobos. Orden propuesto: puntos descendente, cantidad descendente, userId ascendente; position ordinal estable. Totales de miembros incluyen ambos roles; labels deben decir miembros cuando proceda. Participación = miembros con al menos un logro / miembros, cero si no hay miembros. Media debe indicar unidad (puntos o logros por miembro), nunca copiar “4,6” sin definición. Más raro = mínimo count positivo; distinguirlo de no conseguido. Empates de logros por id ascendente. Feed por fecha desc/id desc, últimos creados por createdAt desc/id desc.

Lecturas pequeñas pueden agrupar filas scoped una vez en memoria: evitar una consulta por jugador. Reutilizar el cálculo del ranking para dashboard/jugadores. No añadir caché, tablas de estadísticas, tareas periódicas, snapshots semanales o repositorios genéricos. Índices ya útiles: membresía teamId y unique(userId,teamId), UserLogro unique(userId,logroId), solicitudes userId/createdAt y status/createdAt. Candidatos concretos para la implementación: Logro(teamId,createdAt), UserLogro(logroId,fecha), SolicitudLogro(logroId,status,createdAt). Confirmar necesidad con las consultas finales; no añadir todos preventivamente.

El motivo de rechazo de obtención es una excepción de escritura **exigida por UI-G8/PLAN y la referencia de detalle**, no una nueva fase: añadir `rejectionReason String?`, validar body `{reason}` no vacío (máximo 500), persistir al rechazar y devolver al autor/admin. Mantener compare-and-set PENDING. Campos históricos pueden quedar null y mostrarse como sin motivo registrado; no inventar una razón retroactiva.

## Contrato mínimo propuesto para T04

Persistencia `AchievementProposal` (o equivalente coherente): id, teamId, userId, nombre, descripcion, criterios (`String[]`), status PENDING/ACCEPTED/REJECTED, rejectionReason nullable, createdAt, reviewedAt nullable y logroId nullable/unique. Relacionar Team/User/Logro. Índices probables `(teamId,status,createdAt)` y `(teamId,userId,createdAt)`. No almacenar imagen, URL, temporada, secreto, evidencia, comentarios ni estados adicionales. Añadir criterios a Logro para que sobrevivan a la incorporación; `[]` para catálogo histórico. Añadir createdAt con migración compatible; fechas históricas desconocidas no deben presentarse como fecha histórica exacta.

- `POST /propuestas`: miembro, body `{nombre,descripcion,criterios}`; teamId y userId salen de URL/sesión. Strings trimmed con límites; criterios no vacíos y cantidad acotada. Categoría/puntos sugeridos son campos del mockup, no del acuerdo funcional mínimo: no introducirlos obligatoriamente para PLAYER. El TEAM_ADMIN los fija al aprobar porque Logro.puntos ya es obligatorio.
- `GET /propuestas`: solo autor dentro del tenant; incluye logroId resuelto y motivo. Los detalles personales permanecen dentro de la URL solicitudes.
- `GET /admin/propuestas` con filtro de estado y `GET /admin/propuestas/:id`: TEAM_ADMIN, scoped; incluir autor id/displayName/email y contenido íntegro.
- `POST /admin/propuestas/:id/aceptar`: TEAM_ADMIN; body mínimo `{puntos,categoria?}`. Validar entero no negativo y categoría opcional. Una transacción reclama PENDING mediante compare-and-set, crea **un Logro** con nombre/descripcion/criterios del contenido revisado y enlaza logroId/fecha. No crea UserLogro ni SolicitudLogro. - `POST /admin/propuestas/:id/rechazar`: TEAM_ADMIN, `{reason}` obligatorio; PENDING → REJECTED, motivo y reviewedAt, sin crear catálogo.
- Extender `POST /logros` administrativo para conservar descripcion/categoria/criterios de creación directa con validación; mantener compatibilidad con el body antiguo nombre/puntos. No habilitar publicación directa a PLAYER.

No hace falta framework nuevo ni una separación masiva de capas. Extraer solo el cálculo compartido y la transacción si evita duplicación real. Ante IDs ajenos consultar siempre id+tenant (+autor para vista personal), devolver 404; falta de sesión 401, miembro sin rol 403, body inválido 400, transición repetida 409. Probar que el cliente no pueda imponer teamId/userId/status/logroId.

## Decisiones que debe resolver el Coordinator

Architecture menciona cambiar rol y retirar miembros, y la referencia de invitaciones dibuja revocar/regenerar. **No existen hoy esas escrituras y T03 se titula read APIs**. Esta auditoría no las autoriza por sí misma ni permite cerrarlas con botones falsos. Antes de UI-G8, el Coordinator debe incorporar explícitamente al contrato UI el mínimo indispensable, o documentar que la primera convergencia preserva solo las acciones existentes (crear/copiar invitación y asignar/revisar), adaptando la composición. Si incorpora cambios de rol/retirada, definir protección del último TEAM_ADMIN, efectos sobre logros históricos y rechazo de escalada; si incorpora revocación, conservar autorización por tenant y caducidad/cupo. No implementar estas decisiones dentro de la auditoría.

El agregado de actividad solo puede afirmar hechos persistidos: obtención, creación del catálogo, creación/revisión de solicitudes/propuestas, alta de membresía. No atribuir un revisor o consumidor de invitación cuando no se guarda. No añadir un sistema general de auditoría para rellenar el rail.
