# 7.10 — Piloto local de almacenamiento en Windows

Actualización 2026-10-18: `docker-compose.media.yml` fija `GOMEMLIMIT: 384MiB` en SeaweedFS. Es un objetivo flexible del runtime de Go para ajustar su recogida de basura; no reserva esa RAM ni impone un máximo RSS o cuota Docker. Se aplica con `docker compose -f docker-compose.media.yml up -d`, que recrea el servicio conservando el volumen nombrado `/data`. No usar `down -v`. Se mantiene `mini -dir=/data`, imagen 4.47, S3 privado y puerto loopback. [Carga del flujo integrado](MEDIA-LOAD-TESTING.md). Las notas siguientes conservan la foto histórica de septiembre.

Estado comprobado el 2026-09-29: **piloto local y adaptador S3 básico verificados, incluida persistencia tras recreación; imágenes de la aplicación pendientes**. Esta ficha registra lo observado, no cierra MEDIA-10A-T04 ni acredita integración de imágenes en la aplicación.

- Compose exclusivo: `docker-compose.media.yml`, proyecto `weblogros_media_windows`. No se ha arrancado el Compose general ni creado otra base de datos.
- Imagen: `chrislusf/seaweedfs:4.47`; índice publicado y descargado `sha256:ce9e796f1fe6f06968f4c04bdaf8f678dad9c8acdfef3d244133d71bfa6bf882`, manifiesto Linux amd64 `sha256:f83509b0721dfd8e2e07faf76c0a899f67a8a889c89abe2fa0a5227ba1320362`. La imagen declara `mini -dir=/data`, versión 4.47 y licencia Apache-2.0.
- Datos: volumen nombrado `weblogros_media_windows_data` montado en `/data`, creado por Compose; el montaje se comprobó con `docker inspect`. No borrar este volumen al recrear el contenedor.
- Acceso: solo `127.0.0.1:8333` publicado para S3. Credenciales y bucket configurados mediante `.env.media.local`, ignorado por Git; no se copian sus valores a documentos. Una petición S3 sin credenciales devolvió HTTP 403. La consola interna `weed shell` confirmó el bucket `lockerboard-media-dev` vacío. Una consulta S3 al bucket firmada con las credenciales del contenedor devolvió HTTP 200; esta segunda prueba sí acredita autenticación básica.
- Estado tras el primer arranque: contenedor `weblogros_media_windows-seaweedfs-1` en `running`; muestra instantánea de `docker stats`: 69,25 MiB y 1,16 % CPU. No son máximos ni presupuesto validado.
- Operaciones S3 guiadas: `PUT` de `verificacion/conexion.txt` con texto `prueba-7.10` devolvió 200; `GET` devolvió los mismos bytes y 200; `HEAD` devolvió 200 con `Content-Length: 11` y ETag `a16d703776a626ebcffe3148a9f96973`.
- Persistencia: `docker compose up -d --no-deps --force-recreate --pull never seaweedfs` sustituyó el contenedor (ID anterior `4af7dbe445da`, nuevo `62770ca17711`). Se confirmó de nuevo el montaje `weblogros_media_windows_data -> /data`. GET devolvió `prueba-7.10` y 200; HEAD devolvió 200, 11 bytes y el mismo ETag.
- Borrado: tras `DELETE` del objeto de prueba, HEAD autenticado devolvió 404 y ListObjectsV2 devolvió HTTP 200 con cero claves visibles. `weed shell s3.bucket.list` aún mostró `size:104 logical:71`; esta cifra interna no representa una clave S3 accesible y su comportamiento de espacio físico se medirá por separado. No se ejecutó vacuum ni se borró el volumen.
- Configuración del backend Windows: `apps/backend/.env.ui-windows` contiene `S3_ENDPOINT=http://127.0.0.1:8333` y `S3_BUCKET=lockerboard-media-dev`; ambos archivos locales están ignorados por Git. Node 24 recibió también las credenciales desde `.env.media.local` usando dos argumentos `--env-file`, sin imprimirlas: endpoint/bucket esperados y presencia de access key/secret confirmadas.
- Adaptador backend: `@aws-sdk/client-s3@3.1141.0` fijado en `package-lock.json`. `src/config/objectStoreEnv.ts` valida la configuración cuando se crea el adaptador; `src/lib/objectStore.ts` encapsula Put/Get/Head/Delete, devuelve `null` para una clave inexistente y propaga errores de permisos/servicio. La lectura entrega un flujo, sin abrir el bucket al navegador. El SDK usa endpoint y credenciales configurables, path-style local y checksums solo cuando S3 los exige. Todavía no hay rutas de subida/lectura, modelos de imagen ni integración UI.
- Prueba de integración SDK contra SeaweedFS 4.47: objeto temporal único; Head antes de guardar = ausente; Put, Head y Get = mismo contenido/tamaño/tipo; Delete y Head posterior = ausente; firma con secreto incorrecto = 403. Se eliminó la clave temporal en `finally`. `npm run build` PASS y el archivo compilado ejecutado directamente PASS. `node --test` no pudo iniciar proceso hijo (`spawn EPERM`) en el sandbox; ejecutar el archivo directamente sí utilizó `node:test` y terminó con 1/1 pruebas PASS. Para repetirla desde `apps/backend`, después de compilar: `node --env-file=../../.env.media.local --env-file=.env.ui-windows dist/lib/objectStore.integration.test.js`. Los archivos de credenciales no se versionan ni se imprimen.
- Persistencia con el adaptador SDK, 2026-09-29: Docker Desktop estaba apagado al comenzar; se arrancó fuera del sandbox porque dentro fallaba el acceso a su log/WSL. Se inició **solo** el contenedor SeaweedFS existente, que montaba `weblogros_media_windows_data -> /data`. El SDK guardó un objeto temporal único de 17 bytes (`persistencia-7.10`) y Head devolvió ETag `5713c8067a58c72f9835903437eb2c30`. Compose recreó **solo** SeaweedFS con `up -d --no-deps --force-recreate --pull never seaweedfs`, sin `down -v`: ID anterior `62770ca17711`, nuevo `cb5a52f723e8`; el volumen montado siguió siendo el mismo. El SDK volvió a obtener los 17 bytes idénticos y el mismo ETag. Después Delete y Head confirmaron que la clave temporal ya no existe. No se arrancó PostgreSQL ni el Compose general.

Pendiente medir recursos y espacio bajo carga representativa, definir presupuesto operativo y diseñar rutas/permisos/referencias antes de subir imágenes reales. La [FAQ oficial](https://github.com/seaweedfs/seaweedfs/wiki/FAQ#why-files-are-deleted-by-disk-spaces-are-not-released) explica que el espacio de objetos borrados puede liberarse al compactar volúmenes; no se infiere aquí que los contadores observados tengan esa causa concreta. [Node documenta la carga de varios `--env-file`](https://nodejs.org/download/release/v24.15.0/docs/api/cli.html#--env-filefile).
